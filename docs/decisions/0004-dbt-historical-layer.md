# ADR 0004: dbt historical layer (star schema, SCD2, incremental marts)

- **Status:** Accepted (Phase 4, 2026-10-10)
- **Scope:** `dbt/`, `scripts/reconcile_marts.py`, `scripts/gen_zone_seeds.py`, `snowflake/01-02` (STAGING schema)

## Context

P3's Dynamic Tables answer "what is happening now". The business also needs history:
- GMV and AOV over time
- cohort retention
- restaurant performance trends
- dimensions that remember how things *were*

It has to be tested, documented and explainable. The data is ~100 days of backfill (230,840 orders, 1.35 M events) plus live streaming on top.

## Decisions

### 1. dbt Core 1.12.5 + dbt-snowflake 1.12.1, run locally
Pinned versions released more than two weeks before this decision. `profiles.yml` reads everything from `.env` (key-pair auth, role `FOODDEL_TRANSFORM`, warehouse `WH_TRANSFORM`). Defaults let `dbt parse` run offline in `make test`, while the data tests run in Snowflake as part of `make dbt`.

*Rejected:* dbt Projects on Snowflake. It means less local tooling, but it's harder to test offline and newer to explain. It's a reasonable P8 option for scheduling.

### 2. Sources = SILVER Dynamic Tables, not BRONZE
Dedup and order lifecycle are solved once in SILVER, and reconciled 37/37 in P3. Re-implementing them in dbt would create two versions of the truth that can drift apart. dbt's job is dimensional modelling, history and tests.

### 3. Layers and schemas
| Layer | Schema | Materialization |
|---|---|---|
| staging (`stg_*`) | STAGING | view |
| intermediate (`int_*`) | STAGING | table |
| marts (`dim_*`, `fct_*`, `mart_*`) and seeds | MARTS | table / incremental |
| snapshot | STAGING | snapshot |

STAGING is new: `FOODDEL_TRANSFORM` can create in it, and BI can't read it. A `generate_schema_name` override keeps the names exact, so there's no `MARTS_STAGING`.

### 4. Star schema
- **Fact:** `fct_orders`, one row per order, with foreign keys to every dimension.
- **Dimensions:** `dim_restaurant` (SCD2), `dim_customer` (cohort month, lifetime value, PII), `dim_zone` (seed), `dim_driver`, `dim_date` (`dbt_utils.date_spine`).
- **Marts:** `mart_daily_kpis` (day × zone: GMV, AOV, delivered/cancel/SLA %), `mart_cohort_retention` (cohort month × months since first order), `mart_restaurant_daily`.

### 5. SCD2 from the event log, plus a dbt snapshot for the standard mechanism
- **Event-sourced history:** `dim_restaurant` comes from `RESTAURANT_UPDATED` events, with `valid_from` = change time and `valid_to` = next change (`LEAD`). The first version is open-ended to 1900, so every order finds one. A dbt snapshot records state *when dbt runs*, so loading 100 days of history at once would have collapsed every change into one version. Our source already timestamps each change, and that is the correct history.
- **Re-announcement noise is collapsed:** each simulator run re-announces every restaurant's baseline state, so consecutive identical states (by `HASH` of the attributes) don't count as new versions.
- **`snap_restaurants`** (check strategy) shows the standard mechanism. It's what you'd use for a source that only exposes current state, and it captures changes between dbt runs from P4 on.
- **Facts join point-in-time:** `placed_ts >= valid_from AND placed_ts < valid_to`. In the verification, every order of a restaurant with 7 versions saw exactly the rating valid when it was placed.

### 6. Incremental `fct_orders`: merge on `order_id` with a 24 h lookback
Each run re-merges orders whose newest event was emitted within 24 h of the latest one already loaded, so late (up to 6 h) and out-of-order events update existing rows. The run after a live session showed `rows_inserted = 7, rows_updated = 2414`: the lookback window was re-merged and the new orders were added. A bulk load of *older* history needs `--full-refresh`, as the model's comment documents.

### 7. Seeds come from the simulator
`zones.csv` and `zone_cells.csv` are generated by `scripts/gen_zone_seeds.py` from `pune_zones.yaml`, and a unit test fails if they go stale. The dashboards and the simulator can't disagree about zones.

### 8. Tests and proof
- **39 dbt tests:**
  - generic: unique / not_null / relationships on every key, `accepted_values`
  - `dbt_utils.expression_is_true` (total = subtotal + fees − discount)
  - unique combinations on mart grains
  - singular tests: delivered ⇒ picked up; SCD2 never overlaps and has exactly one current version; daily KPIs add back up to the fact table; cohort month 0 = 100%
  - source freshness on `SILVER.ORDERS`
- **`make reconcile-marts`:** recomputes 35 metrics straight from `data/backfill/*.jsonl.gz` with plain Python and compares them with MARTS: orders, delivered, cancelled and their reasons, SLA breaches, GMV, AOV, per month, per zone, cohort sizes and month+1 retention. **35/35 match.**

## Trade-offs
- **No CI for dbt yet.** `make test` only runs `dbt parse`, because the data tests need a warehouse; CI wiring comes in P8. CLAUDE.md's "make test = pytest + dbt test" is deliberately split so local checks stay free.
- **Lookback by emitted time.** It fits streamed data, but a backfill of older dates won't be picked up incrementally.
- **dbt reads Dynamic Tables.** Marts are only as fresh as SILVER's last refresh; dbt doesn't trigger one itself (P5's Airflow DAG will run `dt-refresh` → `dbt build`).
- **dbt runs as my personal key** for now; a service user for CI and Airflow comes in P5/P8.
- **Seeds are tiny (204 rows).** Fine as seeds; anything larger would belong in a loaded table.
